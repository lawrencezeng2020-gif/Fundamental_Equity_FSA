## 1. Objective

One-click pipeline: enter a ticker in an Excel control panel, press a macro button, receive a
new Excel workbook containing

1. a **Financials** sheet — normalized, formatted income statement, balance sheet and cash flow
   statement pulled from SEC EDGAR filings (10-K / 10-Q), and
2. a **DCF** sheet — a *live, formula-linked* discounted cash flow model whose highlighted input
   cells (revenue growth, margins, WACC components, terminal growth, etc.) drive an implied
   equity value and implied share price that recalculate natively in Excel.

### Non-goals (v1)
- No comps / precedent transactions / LBO / DDM (architecture leaves room; not built).
- No foreign private issuers (20-F / 40-F filers) — US domestic 10-K/10-Q filers only.
- No real-time market data feed beyond a single price input (see §11, Decision D1).
- No multi-ticker batch mode, no scheduling, no server.

### Definition of done
`python -m fsa.cli --ticker AAPL` produces a workbook where a user can change the cell
`Revenue growth — Year 1` and watch the implied share price change, with every intermediate
number traceable to either an input cell or a SEC-sourced figure on the Financials sheet.

## 2. Design decision: fetch-on-demand vs. local historical database

**Question posed:** should we hit the SEC API every run, or bulk-download filings into SQLite?

**Recommendation: fetch on demand, backed by a persistent local response cache. Do not build a
historical filing warehouse.** The owner's instinct is correct, with one amendment.

### Why fetch-on-demand wins here

The decisive fact is the shape of the `companyfacts` endpoint:

```
https://data.sec.gov/api/xbrl/companyfacts/CIK##########.json
```

This returns **every XBRL fact the company has ever tagged, for every period, from every filing**,
in a single HTTP request. It is not a "latest filing" endpoint — the full 10+ year history arrives
in one response. So the usual argument for a local warehouse (avoiding N requests to reassemble
history) simply does not apply. A full run costs **3 requests**: ticker→CIK map, `submissions`,
`companyfacts`. That is 3 of the 10 requests/second SEC permits — a rounding error.

Against a warehouse specifically:
- **Volume:** full EDGAR filing corpus is hundreds of GB. Even the quarterly *Financial Statement
  Data Sets* are ~50–100 MB per quarter and need ~40 quarters to match what one `companyfacts`
  call gives you for the ticker you actually care about.
- **Staleness is a liability, not a feature.** A DCF is forward-looking off the *most recent*
  filings. A warehouse introduces a sync obligation whose only failure mode is silently valuing a
  company on stale numbers.
- **Restatements.** SEC re-serves corrected facts through the same endpoint. A warehouse has to
  detect and reconcile restatements; fetch-on-demand gets the corrected view for free.
- **Cost of being wrong is low.** If the SEC is unreachable, the tool fails loudly and the user
  retries. There is no SLA to protect.

### The amendment: cache, don't warehouse

Add a **response cache**, which is a different thing from a database of filings:

- Store the *raw JSON responses*, keyed by CIK + endpoint, on disk under `.cache/` (SQLite is an
  acceptable container — one file, no server, and it makes eviction and metadata queries easy;
  plain gzipped JSON files are also fine and simpler. Implementer's choice, see Phase 1).
- Use a TTL (default 24h), after which the entry is refetched. **Correction, verified in Phase 1:**
  `data.sec.gov` returns **no `ETag`, `Last-Modified` or `Cache-Control`** on `submissions` or
  `companyfacts` responses, so conditional GET / 304 revalidation is impossible for the two endpoints
  that carry the actual data. Only the static `www.sec.gov/files/company_tickers.json` sends a
  validator (`Last-Modified`), and conditional GET is used there. For the other two, a fresh entry
  means **no request at all** — which is the cache's real benefit — and an expired entry means a full
  refetch. (`HEAD` against `data.sec.gov` returns 403; validators must be checked with `GET`.)
- `--no-cache` and `--refresh` flags to force a live fetch.

The cache earns its keep for four reasons that have nothing to do with saving SEC bandwidth:
1. **Development and test velocity.** Subagents will run this pipeline hundreds of times. Without
   a cache, that is hundreds of unnecessary SEC round trips and slow test suites.
2. **Offline work.** The tool keeps working on a plane.
3. **Reproducibility.** A workbook can be regenerated byte-identically from the exact data snapshot
   it was built from — which matters when you are asked "where did this number come from?"
4. **Provenance.** Alongside each cached response we record accession numbers and filing dates, which
   the workbook's `Info` sheet surfaces as an audit trail.

**Verdict: fetch-on-demand + revalidating cache. Revisit only if a future feature needs
cross-sectional screening across thousands of tickers — that, not history depth, is the workload
that would justify a warehouse.**

## 3. Architecture

```
┌──────────────────────────────┐
│ FSA_Control.xlsm             │   Excel (macOS)
│  Control sheet: ticker, opts │
│  [Generate Model] ──VBA──────┼──► Shell(): python -m fsa.cli --ticker XYZ --out DIR
└──────────────────────────────┘        │
                                        ▼
                        ┌───────────────────────────────────┐
                        │ fsa.sec       — HTTP, rate limit, │
                        │                 cache, CIK lookup │
                        ├───────────────────────────────────┤
                        │ fsa.normalize — XBRL facts ──►    │
                        │                 canonical model   │
                        │                 (IS/BS/CF, LTM)   │
                        ├───────────────────────────────────┤
                        │ fsa.excel     — writes Financials │
                        │                 + DCF as FORMULAS │
                        └───────────────────────────────────┘
                                        │
                                        ▼
                            <TICKER>_DCF_<YYYYMMDD>.xlsx
                                        │
                        VBA reopens it in Excel when done ◄─┘
```

**Hard rule that shapes everything:** the Python layer writes **Excel formulas**, not computed
values. No DCF arithmetic is performed in Python and pasted in as constants. If a cell's value
depends on an assumption, that cell contains a formula referencing the assumption cell. Python's
only numeric outputs are (a) historical figures sourced from SEC and (b) default values seeded into
input cells.

**Second hard rule:** the CLI is the product; Excel is a front-end. Everything must be exercisable
via `python -m fsa.cli` with no Excel present. This is what makes the work testable and what lets
subagents verify their own output.

## 4. SEC compliance and rate limiting

Non-negotiable, enforced in `fsa/sec/client.py`:

- **User-Agent header on every request**, format `Name email@domain` — SEC returns 403 without it.
  Sourced from config, with a first-run prompt if unset. Never hardcode.
- **Token-bucket limiter at 5 req/s** (SEC permits 10; we take half the budget as margin). Shared
  across the process, thread-safe.
- **Backoff:** exponential with jitter, honoring `Retry-After`. Max 5 attempts on 429/5xx. **403 is
  retried at most twice** — SEC has historically used it for throttling, but it is also what a bad or
  missing `User-Agent` returns, which no amount of retrying fixes. The terminal error for a 403 must
  include a snippet of the response body so a policy/UA rejection is diagnosable rather than looking
  transient. **404 is never retried.**
- **`Accept-Encoding: gzip`** — `companyfacts` payloads reach tens of MB uncompressed.
- **Single pooled session**, keep-alive.
- Requests are logged (endpoint, status, bytes, cache hit/miss) so throttling behavior is auditable.

Given the 3-requests-per-run architecture, we will never approach the limit in normal use. The
limiter exists to make that a guarantee rather than an assumption, and to protect against a future
loop over tickers.

## 5. Data normalization — where the real difficulty lives

Pulling the JSON is easy. Turning heterogeneous XBRL tags into a comparable statement is the hard
part, and it is where I expect the most subagent iteration. Documented pitfalls the implementer
must handle explicitly, each with a test.

**Empirical grounding.** The rules below are not hypothetical. They were derived by inspecting live
`companyfacts` responses for KO, MSFT, TSLA, RDDT and CAVA during planning; the specific findings are
cited inline. Phase 2 must reproduce each cited finding as a test.

### 5.1 The period axis rule (read this first)

Establish the fiscal-year axis **once**, from the anchor line item (revenue), using the company's
fiscal year end from `submissions`. Then fill every other line item **per period against that axis**,
leaving an explicit gap where a period has no fact.

**Never** take "the last N periods this tag happens to have." That rule silently misaligns series.
Observed: scanning TSLA for `DepreciationDepletionAndAmortization` and taking its most recent 5 annual
values returns **FY2013–FY2017** — Tesla stopped using that tag after 2017. A model built that way
populates D&A with eight-year-old figures, feeds them into the FCF build, and produces an implied
share price that looks entirely reasonable. This is the single most dangerous bug class in the project.

### 5.2 Mapping mechanisms

`mappings/us_gaap.yaml` maps each canonical line item to us-gaap tags. It must support **three**
mechanisms, not one:

1. **Alternatives** — a priority-ordered list of tags that mean the same thing; the highest-priority
   tag with a value for a given period wins.
2. **Per-period stitching** — different periods on the same axis may be satisfied by *different* tags.
   Accounting-standard transitions deprecate tags mid-history. **Tag adoption is not monotonic**, so
   never assume a single clean pre/post-standard split: verified for TSLA, where
   `RevenueFromContractWithCustomerExcludingAssessedTax` is present FY2018, **absent FY2019–2020**,
   and present again FY2021–2025, alternating three times over a 10-year window. Per-period
   resolution handles this; "pick the tag with the best overall coverage" does not.

   Where tags overlap, values must be compared and any disagreement flagged, not silently resolved.
   **Correction (Phase 2, verified live):** an earlier draft of this document claimed KO's
   `SalesRevenueGoodsNet` and `Revenues` agree in both overlap years. They do not. After latest-filed
   deduplication:

   | FY | `Revenues` | `SalesRevenueGoodsNet` | |
   |---|---|---|---|
   | 2016 | 41.863bn (filed 2019-02-21) | 41.863bn (filed 2018-02-23) | agree |
   | 2017 | **36.212bn** (filed 2020-02-24) | **35.410bn** (filed 2018-02-23) | **2.3% apart** |

   The FY2017 gap is the ASC-606-restated figure against the never-restated retired tag. The original
   claim came from comparing rounded value *sets* rather than applying the dedup rule first — a
   reminder that overlap agreement must be tested after deduplication, not before.
   `STITCH_DISAGREEMENT` tolerance is **0.5% relative**, sized against two real cases: TSLA FY2018
   (0.125% apart, later-filing rounding — agreement) and KO FY2017 (2.3% — flagged).
3. **Composition** — a canonical line may be defined as the **sum of component tags** when no
   aggregate tag exists. This is mandatory, not optional. Observed: **neither MSFT nor TSLA reports
   `DepreciationDepletionAndAmortization` in recent years**; both report `Depreciation` +
   `AmortizationOfIntangibleAssets` + `FinanceLeaseRightOfUseAssetAmortization` separately. A
   mapping supporting only alternatives yields *no D&A at all* for Microsoft.

Whichever mechanism resolved a given cell is recorded and surfaced in the workbook's provenance
column, so a user can audit why a number is what it is.

### 5.3 Pitfall register

Each item requires a passing test in Phase 2.

1. **Tag variance (temporal and cross-sectional).** Handled by §5.2. Note that a shorter history
   window reduces but does not remove exposure: at a 5-year window revenue resolves to a single tag
   for KO, MSFT and TSLA, but that is an artifact of the ASC 606 boundary having aged out of the
   window, not a property of the design — and it does nothing for the D&A composition problem, which
   breaks at **both** 5- and 10-year windows.
2. **Restatements / duplicate facts.** The same `(start, end)` period appears multiple times with
   different `filed` dates and `accn`. → Deduplicate by `(start, end, unit)` taking the fact with the
   **latest `filed`**; where present, a fact carrying SEC's `frame` key is a strong corroborating
   signal, as SEC selected it as canonical for that calendar period. Retain the accession number for
   provenance — determining which figure is *correct* may require reading the filing, which is exactly
   why provenance is surfaced. Observed: KO FY2018 revenue returns $31.86bn (filed 2019-02-21) and
   $34.30bn (filed 2020-02-24 and, with `frame` set, 2021-02-25).
3. **Duration vs. instant.** IS and CF facts are durations (`start`+`end`); BS facts are instants
   (`end` only). Mixing them is a silent correctness bug. Schema enforces the distinction.
4. **Fiscal calendars.** `fy`/`fp` fields are unreliable. → Derive periods from `start`/`end` dates
   and the company's fiscal year end from `submissions`, not from `fy`/`fp`.
5. **Annual vs. quarterly durations.** A 365-day duration is a fiscal year; ~90-day is a quarter.
   Tolerance windows required (a "year" can be 358–378 days; 52/53-week filers exist).
6. **Sign conventions.** `PaymentsToAcquirePropertyPlantAndEquipment` is reported as a *positive*
   number meaning a cash outflow. Every mapped line item carries an explicit sign convention in
   the YAML so the model's arithmetic is unambiguous.
7. **Units.** Facts are keyed by unit (`USD`, `USD/shares`, `shares`). Never mix. Reject or flag
   non-USD reporting currencies in v1.
8. **Missing line items / extension-tag gaps.** `companyfacts` returns **only SEC-standard
   taxonomies**. Sampling KO, MSFT, TSLA and NVDA returned only `us-gaap`, `dei`, `srt`, `ecd`,
   `invest`, `ffd` — **no company-specific extension namespaces**. So there is no custom taxonomy to
   parse, and no per-company taxonomy-resolution code is needed. The failure mode is the inverse: a
   line item tagged *only* with a company extension is absent from the API entirely and appears as a
   **gap**. → Never silently zero-fill. Emit a `#N/A`-equivalent, mark the row, and list every gap on
   the `Info` sheet. (Phase 1 should confirm the namespace finding across the full test-ticker set
   rather than assume it.)
9. **Financial-sector filers.** Banks, insurers and REITs have statement structures where an
   unlevered-FCF DCF is conceptually inappropriate. → Detect by SIC code from `submissions` and
   emit a prominent warning on the `Info` sheet; still generate the model (see Decision D4).
10. **Thin public history.** Young filers may have fewer years than the requested window. Note that
   10-Ks carry XBRL-tagged prior-year comparatives, so available history runs roughly
   **years public + 2**. Observed: RDDT (IPO Mar 2024) has revenue from FY2022; CAVA (IPO Jun 2023)
   from FY2021. → Degrade gracefully: display what exists, label it, seed assumption defaults from
   the available years, and warn on `Info` and atop the DCF when history is under 3 years that the
   seeded assumptions are weakly supported. See §12 for why S-1 ingestion is deferred.

11. **Registrant succession / CIK changes.** A ticker may resolve to a *new* registrant CIK that
   holds almost no filing history, while the company's real history sits under a predecessor CIK that
   no longer carries the ticker. **Verified:** `company_tickers.json` maps `XOM` →
   CIK 2115436 ("ExxonMobil Holdings Corp"), whose `companyfacts` has 94 us-gaap tags and **zero**
   annual revenue periods; the actual history — 438 tags, 17 annual revenue years (2009–2025) — lives
   under CIK 34088, whose `submissions.tickers` is now `[]`, so reverse lookup finds nothing either.
   → Ticker-based resolution alone silently yields an empty model for a supermajor. Mitigations:
   (a) a `--cik` override that bypasses ticker resolution entirely; (b) a `REGISTRANT_CHANGE_SUSPECTED`
   warning when the anchor line item yields far fewer periods than requested — distinct from, and
   checked before, the thin-history path (§5.3.10), which would otherwise misclassify a century-old
   filer as a young one. Automatic predecessor discovery is deferred (§12); suggest, do not guess.
   **XOM is now a required regression ticker.**

### LTM (trailing twelve months)

- Flow items (IS, CF): `LTM = most recent FY + latest YTD-through-Qn − prior-year YTD-through-Qn`.
- Stock items (BS): most recent quarterly instant, used as-is.
- If quarterly data is insufficient, fall back to the latest FY and label the column accordingly.
  Never present a partial-period figure as if it were annualized.

## 6. Excel output specification

### 6.1 Cell convention (standard sell-side)
| Style | Meaning |
|---|---|
| **Blue font, light-yellow fill, thin border** | User input / assumption — the only cells to touch |
| Black font | Formula computed on the same sheet |
| Green font | Link to another sheet |
| Grey italic | Metadata / provenance |

Applied consistently via `excel/styles.py`. Input cells additionally get data validation
(numeric ranges) and are collected under a defined name group so they are easy to find.

### 6.2 Sheet: `Info`
Ticker, company name, CIK, SIC/industry, fiscal year end, reporting currency, generation timestamp,
tool version. Table of source filings used (form, period, filing date, accession number, direct
EDGAR URL). List of unmapped/missing line items, and which mapping mechanism (§5.2) resolved each line that
needed one. Warnings: financial-sector filer (§5.3.9), thin public history under 3 years (§5.3.10),
and any overlap-year disagreement between stitched tags. Disclaimer.

### 6.3 Sheet: `Financials`
- Columns: line item label | up to 10 historical fiscal years (oldest→newest) | LTM.
- Blocks: Income Statement, Balance Sheet, Cash Flow Statement, plus a Supplemental block
  (diluted shares, share count from cover page, total debt build, net debt).
- **Raw USD values are written**; display scaling to millions is done with a number format
  (`#,##0,,;(#,##0,,)`) so downstream formulas stay exact. No hand-scaled constants.
- Subtotals (gross profit, EBIT, EBITDA, net debt, etc.) are **formulas summing their components**,
  not fetched values — so a user correcting one input propagates correctly.
- ⚠ **Gaps must not be absorbed by subtotals.** Excel treats a blank cell as zero, so a gap in a
  component would silently understate its subtotal — a missing `long_term_debt` would understate
  `total_debt`, overstate equity value, and produce a wrong share price with no visible error. Gaps
  are therefore rendered as `#N/A` (or an explicit sentinel that propagates), never as blanks or
  zeros, so a subtotal built on incomplete data *visibly* fails instead of lying. This is a required
  Phase 3 test.
- An adjacent, collapsible column group shows the us-gaap tag backing each row.
- Defined names for every row the DCF consumes (`fin_Revenue`, `fin_EBIT`, `fin_Cash`,
  `fin_TotalDebt`, `fin_DilutedShares`, …) so DCF formulas are readable and survive row insertion.

### 6.4 Sheet: `DCF` — the core deliverable

Layout, top to bottom:

**A. Assumptions block (all blue inputs, seeded with sensible defaults from history)**
- Projection horizon (default 5 years)
- Revenue growth % — per projection year (defaults seeded from 3yr historical CAGR)
- EBIT margin % — per projection year (defaults seeded from LTM margin)
- Effective tax rate %
- D&A as % of revenue
- Capex as % of revenue
- Change in net working capital as % of revenue
- Terminal growth rate %
- WACC inputs: risk-free rate, equity risk premium, beta, cost of debt
- **Current market share price** — user input (Decision D1, resolved). Feeds market capitalisation,
  which sets the market-value equity weight in WACC. See the circularity warning below.
- Capital structure weight override — used when the price cell is blank
- **Direct WACC override cell** — if filled, it wins over the whole build (documented on the sheet)
- Mid-year convention toggle (Y/N)
- Diluted shares outstanding (seeded from filings, overridable)

**B. WACC build** — formulas: `CAPM cost of equity = rf + beta × ERP`;
market cap `= current price × diluted shares`; equity weight `We = mktcap / (mktcap + total debt)`
with total debt linked from `Financials`; `WACC = We×Ke + Wd×Kd×(1−t)`. Resolution order, implemented
with nested `IF`: direct WACC override → price-derived weights → manual weight override.

> ⚠ **Circularity.** The price cell must hold the **current market price**, never the model's implied
> price. Feeding implied price into WACC creates a true circular reference (implied price → market cap
> → equity weight → WACC → discount rate → implied price) that Excel will refuse to calculate. The
> input cell is labelled "Current market share price" on the sheet, and the implied-price output cell
> is visually separated from the assumptions block to make the distinction obvious.
>
> **Consequence:** price is now load-bearing, not cosmetic. A blank price cell must fall through to the
> manual weight override rather than producing `#DIV/0!`. This is an explicit test case in Phase 4.

**C. Projection grid** — columns: FY-3, FY-2, FY-1, LTM ‖ P1…P5 ‖ Terminal
| Row | Historical columns | Projection columns |
|---|---|---|
| Revenue | `=fin_Revenue` link | `=prior × (1 + growth_input)` |
| Growth % | computed | `=growth_input` |
| EBIT | link | `=revenue × margin_input` |
| Less: cash taxes | computed | `=−EBIT × tax_input` |
| NOPAT | sum | sum |
| Plus: D&A | link | `=revenue × da_input` |
| Less: Capex | link | `=−revenue × capex_input` |
| Less: ΔNWC | computed | `=−(revenue − prior revenue) × nwc_input` |
| **Unlevered FCF** | — | sum |
| Discount period | — | `=t` or `=t−0.5` if mid-year |
| Discount factor | — | `=1/(1+WACC)^period` |
| PV of FCF | — | `=FCF × factor` |

**D. Terminal value** — Gordon growth `=FCF_n×(1+g)/(WACC−g)`, discounted; with an **exit-multiple
cross-check** (`=terminal EBITDA × exit multiple input`) shown side by side and a toggle for which
one feeds the valuation. Guard against `WACC ≤ g` with an `IFERROR`/`IF` that returns a readable
error string rather than `#DIV/0!`.

**E. Bridge to implied share price**
```
Sum of PV of projected FCF
+ PV of terminal value
= Enterprise Value
− Total debt            (link to Financials)
+ Cash & equivalents    (link to Financials)
− Minority interest
− Preferred stock
= Equity Value
÷ Diluted shares outstanding
= IMPLIED SHARE PRICE          ◄ headline output, boxed and formatted
vs. current price → implied upside / (downside) %
```

**F. Sensitivity tables** — two 2-way grids: WACC × terminal growth, and WACC × exit multiple, both
outputting implied share price.

> **Implementation note (important):** openpyxl cannot write native Excel What-If Data Tables
> (`TABLE()` array formulas). Each sensitivity cell must instead be a **self-contained formula** that
> re-derives the valuation at that (WACC, g) pair, e.g.
> `=(SUMPRODUCT(FCF_range, 1/(1+$col_wacc)^period_range) + FCF_n*(1+$row_g)/($col_wacc−$row_g)/(1+$col_wacc)^n − net_debt)/shares`
> This is fully dynamic and recalculates correctly. Do **not** fall back to Python-computed constants.

`excel/FSA_Control.xlsm`, sheet `Control`:
- `B2` Ticker (validated, uppercased)

### macOS-specific risk (must be de-risked before anything else)
Excel for Mac runs VBA inside an **App Sandbox**. `Shell()` works, but reading/writing paths outside
the sandbox container can require `GrantAccessToMultipleFiles`, and the sandbox may redirect writes.

**Plan A:** plain VBA `Shell()` + `GrantAccessToMultipleFiles` for the output directory, with Python
writing to a fixed, once-granted folder. Zero third-party dependencies.
**Plan B (fallback):** `xlwings` (`RunPython`), which handles Mac sandbox plumbing but adds an addin
and a dependency.

**This is a Phase 0 spike.** A ~20-line throwaway macro proves whether Plan A works on this machine
*before* any real work is built on top of it. Getting this wrong late would be expensive.

VBA source is version-controlled as `.bas` text under `excel/vba/`; the `.xlsm` is a rebuildable
binary artifact.

## 8. Validation strategy

Three layers, because "the workbook opened without error" is not evidence the model is right.

1. **Unit tests** against committed, trimmed SEC JSON fixtures — fact selection, restatement dedupe,
   period classification, sign conventions, LTM math. Offline, fast, deterministic.
2. **Structural tests** on generated workbooks — expected sheets/named ranges exist, input cells
   carry input styling, no cell in the DCF projection grid contains a hardcoded constant where a
   formula is required (this is directly assertable by inspecting cell types, and is the single most
   important regression guard for the "hard rule" in §3).
3. **Numerical cross-check (the one that actually proves correctness).** `reference/dcf_reference.py`
   implements the DCF independently in Python. The generated workbook is force-recalculated and its
   computed implied share price is compared against the reference within tolerance.
   - No LibreOffice on this machine, but **Excel is installed**, so recalculation is driven via
     AppleScript (`osascript` → open, `calculate`, save) and the results read back with
     `openpyxl(data_only=True)`. Installing LibreOffice is the CI-friendlier alternative if the
     AppleScript route proves flaky.
   - **Verified in Phase 0:** the full round trip (open → force recalculate → read a cell → save →
     close) works against Excel for Mac via `osascript`. Two syntax traps were found and must be
     carried into the implementation: `open` requires the POSIX file coerced **`as alias`** (a bare
     POSIX file yields `Parameter error -50`), and `calculate` must be invoked **bare** (or as
     `full rebuild`), not on a workbook object.
   - This test is what catches an off-by-one in a discount period or a sign error in ΔNWC — the
     class of bug that silently produces a plausible-looking wrong price.

Test tickers spanning the failure surface: **AAPL** (clean, well-tagged), **MSFT** (different fiscal
year end, June), **KO** (older tag vintage), **JPM** (financial-sector warning path), and one filer
with known tag gaps to exercise the missing-data path.

## 11. Decisions needed from the owner

**D1 — Current share price source. ✅ RESOLVED (owner, 2026-08-27):** a highlighted user-input cell
for current market price, used to derive the market-value equity weight in WACC, with a manual
capital-structure weight override for when it is left blank. Live market data deferred to a later
phase. Price is therefore load-bearing, not cosmetic — see the circularity warning in §6.4 B.

**D2 — Historical depth.** *Recommendation:* 10 fiscal years where available, gracefully degrading
for younger filers. Cost is zero — it is all in the one `companyfacts` response.

**D3 — Projection horizon.** *Recommendation:* default 5 years, user-configurable to 10 via the
Control sheet, with the DCF sheet laid out to accommodate the maximum.

**D4 — Financial-sector filers (banks, insurers, REITs).** An unlevered-FCF DCF is the wrong tool
for these. *Recommendation:* generate the model anyway, with a prominent warning on `Info` and at the
top of the DCF sheet. Blocking would be paternalistic; warning is honest.

**D5 — Reporting units.** *Recommendation:* raw USD in cells, displayed as millions via number
format. Preserves precision and avoids the classic scaled-constant bug.

**D6 — Contact identity for the SEC User-Agent.** SEC requires a real name and email. *Recommendation:*
read from a gitignored local config file, prompted on first run, so it never enters version control.

## 12. Deferred enhancements (explicitly out of v1)

**S-1 / pre-IPO financials.** Investigated during planning and deferred. `companyfacts` does not expose
registration statements at all — sampling RDDT and CAVA returned facts from `10-K`, `10-Q` and
`DEF 14A` only, with no `S-1` or `424B4`. Ingesting them would require a second, much heavier path:
fetching raw XBRL instance documents from the filing index and parsing them directly, which is also
where company-specific extension tags actually live — reintroducing precisely the custom-taxonomy
problem that `companyfacts` spares us (§5.3.8).

It is also largely unnecessary. Because 10-Ks carry XBRL-tagged prior-year comparatives, available
history runs roughly *years public + 2*, so a company needs only ~3 years public to yield a 5-year
series. The genuinely thin band is companies public under ~12 months — and those are the ones where an
unlevered-FCF DCF is least defensible anyway (typically pre-profit, no normalised capex, growth rates
no terminal formula absorbs credibly). They are handled by the thin-history warning in §5.3.10, and the
user can type over Financials cells by hand.

*Trigger to revisit:* if sub-1-year-public IPOs become a regular part of the workflow.

**Live market data.** Deferred by Decision D1. The price input cell is the seam: a provider (e.g. Stooq
CSV, no API key) can later populate it behind a flag without touching the model.

**Additional valuation methods.** Comps, precedent transactions, LBO, DDM. The workbook assembly layer
is structured so an additional sheet writer can be added without disturbing existing sheets.

### 13.2 Phase 2 canonical schema (`src/fsa/normalize/schema.py`)

This is the spine of the project: Phases 3 and 4 render it, and Phase 7 validates against it.

```python
class Statement(Enum):   INCOME | BALANCE | CASHFLOW | SUPPLEMENTAL
class PeriodType(Enum):  DURATION | INSTANT
class Mechanism(Enum):   DIRECT | ALTERNATIVE | STITCHED | COMPOSED | DERIVED | MISSING
class Sign(Enum):        AS_REPORTED | NEGATED

@dataclass(frozen=True)
class FiscalPeriod:
    label: str                 # "FY2024" | "LTM"
    fiscal_year: int
    end: date
    start: date | None         # None for INSTANT
    kind: PeriodType
    is_ltm: bool
    days: int | None

@dataclass(frozen=True)
class Provenance:
    mechanism: Mechanism
    tag: str | None                      # resolved tag; None when COMPOSED or MISSING
    component_tags: tuple[str, ...]      # populated when COMPOSED
    accession: str | None
    filed: date | None
    frame_corroborated: bool             # SEC's own `frame` key was present (§5.3.2)

@dataclass(frozen=True)
class Cell:
    value: Decimal | None      # None means GAP. Never 0 to represent absence (§5.3.8)
    unit: str                  # "USD" | "USD/shares" | "shares"
    period_label: str
    provenance: Provenance

@dataclass(frozen=True)
class LineItem:
    key: str                   # canonical, e.g. "revenue"
    label: str                 # display, e.g. "Total revenue"
    statement: Statement
    period_type: PeriodType
    sign: Sign
    is_subtotal: bool          # subtotals are NOT populated here — Excel computes them (§6.3)
    cells: Mapping[str, Cell]  # keyed by FiscalPeriod.label

@dataclass(frozen=True)
class DataWarning:
    code: str                  # FINANCIAL_SECTOR | THIN_HISTORY | STITCH_DISAGREEMENT | NON_USD
                               # | REGISTRANT_CHANGE_SUSPECTED  (§5.3.11)
                               # | DEBT_CONVENTION_UNKNOWN       (§5.2)
    message: str
    detail: Mapping[str, object]

@dataclass(frozen=True)
class FinancialModel:
    company: CompanyRef
    currency: str
    fiscal_year_end: str                    # "MMDD"
    periods: tuple[FiscalPeriod, ...]       # THE axis: oldest → newest, LTM last
    line_items: tuple[LineItem, ...]
    warnings: tuple[DataWarning, ...]
```

**Invariants Phase 2 must guarantee, each with a test:**
1. `periods` is constructed **once** from the anchor line item (revenue) and every `LineItem.cells`
   is keyed against it. No line item may introduce a period of its own (§5.1).
2. A missing value is `None`, never `Decimal(0)` (§5.3.8).
3. Every non-missing `Cell` carries a `Provenance` recording which mechanism resolved it.
4. `is_subtotal=True` items carry no fetched values; Phase 3 writes them as Excel formulas.
5. Monetary values are `Decimal`, never `float`.
6. `DURATION` and `INSTANT` values are never mixed within a `LineItem` (§5.3.3).

### 13.3 Mapping file format (`mappings/us_gaap.yaml`)

Must express all three mechanisms from §5.2. Sketch:

```yaml
revenue:
  label: Total revenue
  statement: income
  period_type: duration
  sign: as_reported
  anchor: true              # exactly one line item defines the period axis
  tags:                     # priority-ordered alternatives, stitched per period
    - RevenueFromContractWithCustomerExcludingAssessedTax
    - RevenueFromContractWithCustomerIncludingAssessedTax
    - Revenues
    - SalesRevenueNet
    - SalesRevenueGoodsNet

d_and_a:
  label: Depreciation & amortization
  statement: cashflow
  period_type: duration
  sign: as_reported
  tags:
    - DepreciationDepletionAndAmortization
    - DepreciationAmortizationAndAccretionNet
  compose:                  # used for periods no single tag covers (MSFT, TSLA — §5.2.3)
    - Depreciation
    - AmortizationOfIntangibleAssets
    - FinanceLeaseRightOfUseAssetAmortization
```

Resolution order per period: `tags` in priority order → `compose` if no single tag covers it →
otherwise a gap. Overlap disagreements between stitched tags raise `STITCH_DISAGREEMENT`.

**Subtraction operands must have matching scope.** A derived item that subtracts one tag from
another is only valid if both measure the same population. Counterexample found the hard way: deriving
`long_term_debt = LongTermDebt − short_term_debt` produced **$13M** for TSLA FY2022 (true value
~$1,029M — a 99% understatement flowing into net debt and the implied share price). TSLA's own history
shows `LongTermDebt` *was* the total-including-current in 2011–12 (276.3 = 268.3 + 7.9), but by 2022
the current-side tag had changed to `DebtCurrent`, which includes current finance leases, while
`LongTermDebt` excludes finance leases entirely (corroborated: 1,029 + `FinanceLeaseLiabilityNoncurrent`
568 = 1,597, Tesla's reported "debt and finance leases, net of current portion"). Automatic per-filer
calibration was considered and rejected — the convention is not stable across tag-pair changes within a
single filer. Filers with no noncurrent tag get an honest gap plus `DEBT_CONVENTION_UNKNOWN`, and
`net_debt` is simply unavailable for them. **Verified live: JPM reports no noncurrent, current, or
`DebtCurrent` tag at all after 2014 — its gaps are real, not fixture artifacts.**

**Alternatives must be true synonyms.** Two tags belong in the same priority list only if they mean
the same thing. Counterexample found in Phase 2: `LongTermDebt` (total, *including* the current
portion) and `LongTermDebtNoncurrent` (*excluding* it) are not interchangeable — treating them as
alternatives makes `total_debt = short_term_debt + long_term_debt` double-count the current portion,
which flows straight into net debt and the equity bridge. Tags that measure different things belong
to different canonical items, or are excluded.

**Two additional resolution kinds** (approved in Phase 2, beyond the three mechanisms above):

- `derived: true` — computed in Python from other already-resolved canonical items, recorded as
  `Mechanism.DERIVED`. Used where no tag exists and composition is unsafe. A derived item must be
  *exactly* defined by its inputs; a residual that silently absorbs unrelated items is not acceptable
  (see `change_in_nwc`).
- `cover_page: true` — tolerant forward-looking date matching (0–120 days past period end) for facts
  dated to the filing cover page rather than the fiscal period end. Required for
  `dei:EntityCommonStockSharesOutstanding`: AAPL's FY2025 (period end 2025-09-27) cover-page share
  count is dated 2025-10-17, so exact-date matching yields **100% missing for every company**. Use
  only for genuinely cover-page-dated facts.

```python
class Style(Enum):
    INPUT      # blue font, light-yellow fill, thin border — the ONLY cells a user edits
    FORMULA    # black — computed on the same sheet
    LINK       # green — reference to another sheet
    META       # grey italic — provenance / metadata
    HEADER; SUBTOTAL; TITLE

FMT_USD_MM     = '#,##0,,;(#,##0,,)'   # raw USD in the cell, displayed as millions
FMT_SHARES_MM  = '#,##0,,'
FMT_PER_SHARE  = '$#,##0.00'
FMT_PCT        = '0.0%'
FMT_MULTIPLE   = '0.0x'

GAP_FORMULA = '=NA()'    # renders #N/A and PROPAGATES through SUM — never write a blank for a gap

def apply(cell, style: Style, number_format: str | None = None) -> None
```

**The cell index — how Phase 4 addresses Phase 3's output.** Phase 4 must never hardcode or guess a
cell address. `write_financials_sheet` returns:

```python
@dataclass(frozen=True)
class SheetIndex:
    sheet_name: str
    period_labels: tuple[str, ...]              # axis order; matches FinancialModel.periods
    cell: Mapping[tuple[str, str], str]         # (line_item_key, period_label) -> "Financials!$F$14"
    row_range: Mapping[str, str]                # line_item_key -> "Financials!$C$14:$N$14"
    def ref(self, key: str, period: str) -> str # KeyError if absent — never returns a guess
```

**Sheet writer signatures:**

```python
def write_financials_sheet(wb: Workbook, model: FinancialModel) -> SheetIndex          # Phase 3
def write_dcf_sheet(wb: Workbook, model: FinancialModel, index: SheetIndex) -> None    # Phase 4
def write_info_sheet(wb: Workbook, model: FinancialModel) -> None                      # Phase 5
```

**Binding rules for both phases:**

1. **Gaps render as `GAP_FORMULA`, never blank, never 0.** Excel treats blanks as zero, so a blank
   gap inside a `SUM` silently understates the subtotal (§6.3). `#N/A` propagates and fails visibly.
2. **Subtotals are `SUM`/arithmetic formulas over component cells**, never Python-computed values.
3. **Phase 4 writes formulas, not numbers**, for every projection and valuation cell. The only
   literals it may write are seeded defaults into `Style.INPUT` cells (§6.4A).
4. **A missing `net_debt` must make the implied share price show `#N/A`**, never silently treat debt
   as zero. This is real for TSLA/JPM/RDDT/CAVA today (`DEBT_CONVENTION_UNKNOWN`, §5.2) and is a
   required Phase 4 test.
5. Values are written as raw USD with a display number format; never hand-scale to millions.
6. Phase 4 reads historical values only through `SheetIndex.ref()`.
