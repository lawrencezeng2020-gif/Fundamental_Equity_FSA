# Phase 0 spike: macOS Excel sandbox risk

PLANNING.md Section 7 flags this as the item that must be de-risked before anything is
built on top of it:

> Can VBA `Shell()` in Excel for Mac launch our Python CLI, and can Excel then open a
> workbook file that the Python process wrote to a normal user directory outside Excel's
> sandbox container?

This directory contains the throwaway spike that answers it. Three things were verified
**automatically** (commands and output below); the actual button-press inside Excel
requires **manual** execution and is not something this report claims to have done for
you -- see "What could not be automated" below.

---

## What was verified automatically

### 1. `spike_target.py` runs correctly under an emptied environment

This emulates how VBA `Shell()` invokes a child process: an absolute interpreter path,
no inherited `PATH`, no shell profile, and no meaningful working directory.

```
$ env -i /Users/tsanglarry/work/Projects/Fundamental_Equity_FSA/venv/bin/python \
    /Users/tsanglarry/work/Projects/Fundamental_Equity_FSA/spike/spike_target.py \
    /Users/tsanglarry/work/Projects/Fundamental_Equity_FSA/spike/_manual_test_output

/Users/tsanglarry/work/Projects/Fundamental_Equity_FSA/spike/_manual_test_output/spike_output.xlsx
exit code: 0
```

Reading the resulting file back confirmed it is a valid, openable workbook containing the
interpreter path and a timestamp:

```
('Generated by', 'spike_target.py')
('Timestamp (UTC)', '2026-08-28T22:35:31.502728+00:00')
('sys.executable', '/Users/tsanglarry/work/Projects/Fundamental_Equity_FSA/venv/bin/python')
('os.getcwd()', '/Users/tsanglarry/work/Projects/Fundamental_Equity_FSA')
('PATH env var present?', 'no (expected under env -i / sandboxed Shell())')
('PID', 28579)
```

**Conclusion:** the Python half of the pipeline has no dependency on `PATH`, a shell
profile, or `cwd`, and writes correctly to an arbitrary real directory when given
absolute paths. This is necessary but not sufficient -- it does not yet prove anything
about being launched *from inside Excel's sandbox* (see below).

### 2. Excel is scriptable via `osascript`, and can force-recalculate a workbook

This matters independently: PLANNING.md Section 8 relies on driving Excel via
AppleScript to force recalculation for the numerical cross-check validation layer.

What worked, exactly:

```applescript
tell application "Microsoft Excel"
    open (POSIX file "/abs/path/spike_output.xlsx" as alias)   -- must coerce to `alias`;
                                                                 -- passing the POSIX file
                                                                 -- object directly raised
                                                                 -- "Parameter error (-50)"
    calculate full rebuild                                      -- also works as plain `calculate`
                                                                 -- with no object; `calculate
                                                                 -- active workbook` raised the
                                                                 -- same Parameter error
    set v to value of cell "B3" of worksheet "Spike" of workbook "spike_output.xlsx"
    save workbook "spike_output.xlsx"
    close workbook "spike_output.xlsx" saving no
end tell
```

Full round trip, run from the shell:

```
$ osascript <<'APPLESCRIPT'
tell application "Microsoft Excel"
    activate
    calculate full rebuild
    set theValue to value of cell "B3" of worksheet "Spike" of workbook "spike_output.xlsx"
    save workbook "spike_output.xlsx"
    close workbook "spike_output.xlsx" saving no
    return theValue
end tell
APPLESCRIPT
/Users/tsanglarry/work/Projects/Fundamental_Equity_FSA/venv/bin/python
exit code: 0
```

The returned value matches exactly what `spike_target.py` had written to that cell,
confirming the open -> recalculate -> read -> save -> close cycle works end to end.

**Two syntax traps found**, both worth carrying into Phase 8's implementation and into
`GenerateModel.bas`:
- `open <POSIX file>` fails with `Parameter error (-50)` unless the POSIX file is
  coerced `as alias` first.
- `calculate <workbook object>` (e.g. `calculate active workbook`) fails with the same
  Parameter error. The app-level bare `calculate` or `calculate full rebuild` command
  (no object) works.

**Conclusion:** the AppleScript-driven recalculation approach in PLANNING.md Section 8
is confirmed viable on this machine, with Excel already installed and no LibreOffice
needed.

### 3. Excel's sandbox container path, and a concrete finding about it

```
$ ls ~/Library/Containers/ | grep -i excel
com.microsoft.Excel

Container: /Users/tsanglarry/Library/Containers/com.microsoft.Excel/Data
```

Inspecting that container's contents surfaced a specific, relevant fact:

```
$ ls -la ~/Library/Containers/com.microsoft.Excel/Data
lrwxr-xr-x  ... Desktop -> ../../../../Desktop      <- symlink to the REAL ~/Desktop
drwx------  ... Documents                            <- REAL DIRECTORY, NOT a symlink, and EMPTY
lrwxr-xr-x  ... Downloads -> ../../../../Downloads   <- symlink to the REAL ~/Downloads
lrwxr-xr-x  ... Movies -> ../../../../Movies
lrwxr-xr-x  ... Music -> ../../../../Music
lrwxr-xr-x  ... Pictures -> ../../../../Pictures
```

Desktop, Downloads, Movies, Music, and Pictures are sandbox-exception symlinks straight
through to the real user folders. **`Documents` is not** -- it is a genuine, separate,
empty directory private to the container. This is a concrete, machine-specific
confirmation of the exact risk PLANNING.md Section 7 names in the abstract ("the sandbox
may redirect writes"): Excel's own sandboxed notion of "Documents" is **not** the same
place as the real `~/Documents`, which is where this project's default `output_dir`
(`~/Documents/FSA_Output`, see `fsa/config.py`) points.

This does not by itself mean Plan A fails -- `GrantAccessToMultipleFiles` exists
precisely to let a sandboxed app reach outside its container to a specific path the user
(or a prior file-open dialog) has approved. But it does mean the manual test in the next
section is not a formality: if `GrantAccessToMultipleFiles` fails or silently no-ops for
a path under the real `~/Documents`, that is the sandbox boundary in the release notes
actually biting, not a hypothetical.

## What could not be automated -- the actual manual step

Running a VBA macro requires importing it through Excel's VB Editor and clicking through
Excel's own macro-security prompts; both are interactive by design (Gatekeeper / Office
"Enable Macros" dialogs are not something to script around). **This has not been run.**
Everything above is real, automated evidence; the paragraph below is a procedure for the
repo owner to run it, not a claim that it has already passed.

### Manual procedure (under 5 minutes)

1. Open Excel for Mac. Create a new blank workbook and save it anywhere convenient, e.g.
   `~/Desktop/spike_test.xlsx` (keep macros enabled when prompted).
2. On `Sheet1`, put labels and leave the value cells next to them:
   - `A1: python path` → `B1` = the absolute path to this repo's venv python, e.g.
     `/Users/tsanglarry/work/Projects/Fundamental_Equity_FSA/venv/bin/python`
   - `A2: script path` → `B2` = the absolute path to
     `/Users/tsanglarry/work/Projects/Fundamental_Equity_FSA/spike/spike_target.py`
   - `A3: output dir` → `B3` = an absolute output directory, e.g.
     `/Users/tsanglarry/Documents/FSA_Output_spike` (deliberately under the real
     `~/Documents`, to test the exact finding in section 3 above)
   - `A5: status` → `B5` left blank (the macro writes here)
3. Open the VBA editor: **Tools > Macro > Visual Basic Editor** (or `Option-F11`).
4. **File > Import File...** and select `spike/vba/SpikeShell.bas`.
5. Back in Excel: **Tools > Macro > Macros...**, select `RunSpike`, click **Run**.
6. Read cell `B5`.

### PASS / FAIL criteria

- **PASS:** `B5` reads `PASS: opened <path> written by <python path> at <timestamp>`,
  and a new workbook window (`spike_output.xlsx`) is visibly open in Excel, showing the
  same python path and a fresh timestamp in cells B2/B3 of its `Spike` sheet.
- **FAIL, timeout:** `B5` reads `FAIL: timed out after 30s waiting for ...`. This means
  either `Shell()` did not actually launch the process (check the python/script paths
  for typos, and confirm they're both absolute) or the sandbox blocked the write
  entirely before `GrantAccessToMultipleFiles` ever got a chance to run.
- **FAIL, grant denied:** `B5` reads `FAIL: GrantAccessToMultipleFiles returned False...`.
  This means the file *was* written (Shell/Python side works) but Excel's sandbox
  refused to extend access to it -- the specific failure mode the container inspection
  above flagged as plausible for paths under `~/Documents`.
- **FAIL, VBA error:** `B5` reads `FAIL: VBA error <N> - <description>`. Report the
  number/description; it usually pinpoints which step (Shell, polling, grant, or open)
  broke.

### What a FAIL implies

Per PLANNING.md Section 7, a FAIL here means falling back to **Plan B: `xlwings`**
(`RunPython`), which handles the Mac sandbox plumbing itself at the cost of one
additional dependency and an Excel add-in. That fallback is not built as part of this
spike -- confirm the FAIL first, then decide whether to invest in the xlwings path before
Phase 6 begins.

**One cheaper thing to try first**, before reaching for xlwings: the container
inspection above found that `Desktop` is a symlink straight through to the real
`~/Desktop`, while `Documents` is not -- a real, separate, private directory. If the
FAIL is specifically a `GrantAccessToMultipleFiles` refusal (or `Workbooks.Open` failing
silently) for an output directory under `~/Documents`, re-run the manual procedure with
`B3` pointing at `~/Desktop/FSA_Output` instead, and see whether that alone flips the
result to PASS. This is a hypothesis to test, not a claim it will work -- access to an
arbitrary absolute path from inside the sandbox is ultimately governed by sandbox
permissions and what `GrantAccessToMultipleFiles` is granted, not by which of the
container's internal folders happen to be symlinked. The manual run is what actually
settles it either way.

## Files in this directory

- `spike_target.py` -- the trivial standalone script Shell() launches. Verified working
  under `env -i` (see above). No dependency beyond `openpyxl` (already a project
  dependency).
- `vba/SpikeShell.bas` -- the importable VBA module described in the manual procedure.
  Heavily commented; it is the reference implementation `GenerateModel.bas` (Phase 6)
  will be built from, including the two `osascript`-adjacent gotchas that also apply to
  plain VBA (`Shell()` is asynchronous -- there is no built-in "wait"; poll for the
  output file instead).
